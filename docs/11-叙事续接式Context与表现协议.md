# 叙事续接式 Context、soul 与表现协议

实施更新：已接入 L0–L4、narrative 和受限记忆能力，移除了原型的固定语气命令，见 [模块说明](../src/core/memory/README.md)。动作 / 视觉协议继续预留，初始人物材料未擅自填充。

日期：2026-11-06。状态：用户提出叙事续写方向，本文件为具体组装建议，未实施。动作仅预留接口，Live2D / 3D 仍然搁置。本文不填充初始记忆或最终 soul 文本。

最新用户要求将 soul 放在最底层，允许较长，并提出每日思考与重要记忆权限。具体层级与更新依据见 [12](12-Context内容层级与主线记忆权限.md)，下文“少量人物材料”的早期建议不构成 soul 长度限制。

## 这次需要修正什么

用户将 soul 理解为人物底色、语气等材料，并担心每轮直接命令“用某种语气”会强化扮演感。此前方案几乎把 soul 等同于自传 / 取舍记录，分工不够清晰。

建议将长期人物材料、相处叙事、实际对话分开维护。用既有材料与经历承接下一段表达，减少“你现在必须温柔、开心、像某角色”的逐轮指令。不另加情绪数值状态或导演式状态赋值。

续接式提示仍会引导生成，不能保证仅改变写法就消除扮演感。要验证的是：没有明确语气命令时，是否能从材料中延续自然表达；是否减少复述人设、编造经历、代写用户及过多旁白。

## soul 与相处叙事

| 材料 | 职责 | 更新方式 |
|---|---|---|
| L0 soul / 人物材料 | 较完整的底层人物材料、观察角度、表达方式与重要背景，允许较长 | 初始内容预留；以后按用户提供或有依据的长期变化更新，不每轮为迎合即时情绪改写 |
| L1 相处叙事 narrative.md | 经历与思考沉淀出的当前理解、关系地基与有效取舍；临时未完话题放 L2，具体事件仍在日志和记忆查询中 | 由既有整理线的反思整合提出版本化更新，使用独立 Markdown 投影，不新增整理模块 |
| 近期对话 | 真实用户输入与她实际说过的话 | 由原生 Session 记录，保留 speaker 和顺序 |

soul 可以表达人物特征，但避免全是形容词命令表或固定句式。少量代表性文字可以体现节奏与看待事物的方式，不把固定口癖灌满每轮上下文。

人物故事、写作示例和用户提供的设定应标为材料，不能写入“她与当前用户亲历过”的关系史。新的真实相处也不能被旧材料压回某个预定人格结局。

用户要求的初始记忆仍为空槽。本轮不擅自写好昔涟的初始自传或添加不存在的往事。若以后允许从经历中调整 soul，由整理线提出带来源的长期变更，仍走既有提交链，不增加另一套人格更新 Agent。

## Context 的建议组装

仍使用原生 system-prompt / context snapshot / Session surface 等机制，不在模型调用前私自重建另一份 messages 历史。

| 部分 | 内容 | 特别约束 |
|---|---|---|
| 最小系统约定 | 此次由谁回应、来源与权限边界、必要输出协议 | 保留分权与来源要求，不承担每轮指挥语气的职责 |
| 稳定人物材料 | soul 及允许引用的故事 / 代表性片段 | 内容与真实相处区分；初始位置目前预留 |
| 有限的叙事衔接 | 最新已接受叙事、关系、未完话题与相关回忆 | 写成发生过什么和仍在继续什么，不写“现在应当感动 / 表现出疲惫” |
| 当前场景 | 真实日期、上次活动间隔、直接输入或 15 秒窗口带入的受限工作观察 | 分清观察与推测；不把后台维护动作讲成角色外界经历 |
| 近期原始对话与当前输入 | 原生 user / assistant 消息 | 保留实际角色与归属，不把所有内容打平为可任意续写的小说 |
| 可选表现能力 | 当前可执行的语义动作与简短协议 | 空能力表时不请求动作；不借此要求固定情绪或表演场面 |

这里的“续写”是延续同一个存在的下一句表达及允许的表现，不是代写用户台词、反应、未来经历或完整剧情。现有每日首轮交接的内容范围不变，调整的是材料的组织与表达形式。

新的一天加载当前版本的 L0 soul、L1 narrative 与有限的 L2 交接，不因换日把较长 soul 自动精简；当天的近期原文继续由原生 surface 承载。整理记忆变化时更新对应视图，不每轮重写全部人物材料。Context 压缩后应保留未完话题与有来源的关系变化，不能改成重新下达一次“请扮演某人”。

## 一个只说明组织形式的例子

以下内容是虚构示意，不写入实际 soul 或记忆：

```text
人物材料：
〔预留，稍后由真实来源填入；这里不放“必须温柔、每句不超过几字”的命令〕

此前的相处：
昨天聊过一段文字。用户说想今天改好后再一起读。
这件事还没有结束。

近期真实对话：
〔由原生 Session 提供，保留原来的说话者〕

用户当前输入：
今天把那段文字改好了。
```

回应从已有话题自然接下去。示例中的提示也不是最终模板，实际注入必须保留内部来源引用，且不能为了形成故事感补写没有记录的相处。

## 其他项目怎样处理动作

本轮核对了之前的本地固定版本，并打开了对应上游源码：

### AITuberKit

基准 `91890921e8624001ce1d04a0f59759e1ab5ee334`。模型输出情绪与动作标签；tagExtractors 分离标签和正文，speechDispatcher 将结果构造成 `Talk { message, emotion, motion }`，交给播放队列和具体角色执行器。

```text
[happy][motion:wave]你好。
```

这是协议示例。具体可用动作来自其配置；所读 Live2DHandler 主要以 emotion 映射表情 / 动作组，不能认定 motion 标签在 VRM 与 Live2D 自动等价。

### AIRI

基准 `259b6188a7209a46bd535fa011340486654da8df`。它在流中混入 ACT JSON 标记，普通文本走语音，控制标记走 parser 和 Stage。提示只列已启用的 Live2D expression 与 motion，名称取自角色实际资源。

```text
<|ACT {"expression":{"name":"Smile","duration":3}}|>你好。
```

`Smile` 仅示意，实际必须在注册表中存在。ACT parser 解析对象，不在解析时直接执行；具体执行还需 Stage 和动作注册表。所读显式 motion / expression 分支是 Live2D 路线，不能扩大成所有格式的统一能力。

共同点是台词生成与有限动作意图可以来自同一次回复，但必须拆成独立输出语义。技术控制标记不等于模型自述的情绪事实，也不必展示为聊天中的动作旁白。

## LiveSeed 的接口建议

借鉴流式文本加可选控制标记的方式，内部至少区分两个事件：

- `text`：对用户说的话，用于显示，未来可送入 TTS。
- `actionIntent`：当前能力允许的动作意图，供前端调度器处理。

拟议示例，不是已实现协议，也不宣称直接兼容 AIRI 字段：

```text
<|ACT {"gesture":"nod"}|>嗯，我在听。
```

解析后文本是“嗯，我在听”，动作候选为 `nod`。将来执行器将其映射到具体模型资源。模型不填写文件路径、Live2D 参数或任意骨骼角度。

也可以采用完整结构化响应承载这两个事件，但它对自然流式展示和分段提出不同要求；首版先验证薄标记协议，暂不把最终语法写死。后续不要求逐句都有动作，不另加一个云端动作导演来处理每句话。

动作控制只对模型本次生成的控制区域生效，不能从用户输入、记忆引文或故事里的任意括号直接执行。流式片段先完整识别、schema 校验、检查能力和代际，再投递。非法或未知标记不执行，正文仍尽量可用；需要处理拆包、引用转义与取消，不能简单扫描所有文本中的“微笑”就驱动。

当前没有角色和动作执行器，能力表为空：只预留接口，不注入虚构动作能力，也不启用动作生成。已有原型目前仍直接显示模型文字，不能在没有解析器时先要求输出控制标记。

## 生成动作与发生动作分开

Session 中的生成记录可以保存原始输出；聊天投影拆出文本，动作投影拆出意图和关联片段。模型可见派生历史和 UI 显示可不同，但所有生成与投递应可回溯原生日志。

主模型生成了点头意图，不代表浏览器已点头。未来前端是否支持、是否接收、是否播放及中断是不同执行结果；没有回执不能把“动作已播放”当经历。

整理线抽取真实台词与有依据的结果，不将控制标签、未执行动作、写作示例或重新注入的叙事重复当外界经历。视觉执行不会建立独立情绪数值或改写记忆权限。

## 原型与后续验证

当前 `runtime.ts` 的 persona 仍包含临时的“自然、温暖、简洁”等指令。本轮只记录方案，没有把某个新 soul 或叙事模板直接写进运行时。

下一步以相同真实对话片段比较：指令式语气、叙事衔接、叙事加少量代表文字。检查接话连续性、重复口癖、代写用户、过量旁白、编造经历与成本；不能仅凭提示形式宣布扮演感已消失。

动作暂缓阶段只保留接口方案。实际接入前验证：标记跨 chunk、用户引用标记、未知动作、不支持能力、停止后迟到动作、正文 / TTS 不读标签，以及整理线不误记动作。
